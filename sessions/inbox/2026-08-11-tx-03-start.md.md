## 이번 세션 범위

### 핵심 개념

1. checked exception과 runtime exception의 기본 rollback 규칙
2. `rollbackFor`를 통한 명시적 rollback 규칙
3. `readOnly=true`가 강제 쓰기 금지가 아니라 읽기 전용 힌트라는 점

### 예정된 최소 실험

- 기본 `@Transactional`에서 checked exception과 runtime exception의 최종 DB 상태 비교
- checked exception에 `rollbackFor`를 지정했을 때의 최종 DB 상태 비교
- `@Transactional(readOnly = true)`에서 쓰기를 시도한 뒤 다음 항목 관찰
  - INSERT SQL 실행 여부
  - 예외 발생 여부
  - 트랜잭션 종료 후 최종 DB 상태

### 완료 기준

예외 종류와 명시적 rollback 설정, 실제 호출 경로를 근거로 commit과 rollback을 판단하고, 예외 발생 사실만으로 rollback을 단정하지 않는다.

## TX-02 회상 복습 결과

### 질문 1

`persist() → flush() → RuntimeException` 경로에서 INSERT SQL이 실행됐는데도 DB에 행이 남지 않을 수 있는 이유를 설명한다.

### 학습자 답변

TransactionInterceptor가 RuntimeException을 확인하고 commit 대신 rollback을 요청하면, flush가 수행됐더라도 DB에서 행이 보이지 않을 수 있다고 설명했다.

### 피드백

핵심 방향은 맞았다. 다만 다음 표현을 교정했다.

- 예외는 target 객체에서 반환되는 것이 아니라 target 메서드 밖으로 던져진다.
- `TransactionInterceptor`는 프록시 밖으로 전파되는 예외를 관찰하고 rollback 규칙을 적용한다.
- `flush()`는 SQL을 실행하지만 DB 트랜잭션을 commit하지 않는다.
- 트랜잭션 완료 전 별도 Connection에서 행이 보이지 않는 이유와 rollback 후 행이 남지 않는 이유는 구분해야 한다.
  - 완료 전: `READ_COMMITTED`에서 다른 트랜잭션의 미커밋 변경을 읽을 수 없다.
  - rollback 후: 현재 트랜잭션의 미완료 변경이 폐기됐다.

### 질문 2

`EntityManager.find()` 결과만으로 INSERT SQL 실행 여부를 증명할 수 없는 이유를 설명한다.

### 학습자 답변

기억나지 않는다고 답했다.

### 재설명

`persist()`된 엔티티는 영속성 컨텍스트의 1차 캐시에 존재할 수 있다. 이후 `EntityManager.find()`가 DB에 SELECT를 실행하지 않고 1차 캐시의 같은 객체를 반환할 수 있으므로, 조회 성공만으로 INSERT SQL이 실행됐다고 증명할 수 없다.

지난 실험에서는 같은 Connection의 행 개수가 flush 전 `0`, flush 후 `1`이라는 assertion이 SQL 실행의 근거였다.

### 복습 상태

- flush와 commit의 구분: 부분 회상 성공
- 예외 전파와 TransactionInterceptor의 판정 흐름: 표현 교정 필요
- 1차 캐시와 SQL 실행 증명의 구분: 재복습 필요
