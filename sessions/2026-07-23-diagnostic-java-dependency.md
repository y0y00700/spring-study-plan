# 2026-07-23: 기초 진단 — 의존 객체 생성과 Singleton 공유 상태

## 학습 전 내 생각

- 구체 클래스를 직접 생성하면 생성 책임까지 호출 클래스가 지며, 구현체 변경이 호출 클래스의 변경으로 이어진다.
- 의존 객체를 직접 생성하면 재사용성이 낮아진다.
- Singleton의 변경 가능한 필드에 여러 스레드가 접근하면 의도하지 않은 값을 얻을 수 있다.

## 튜터의 질문

1. 인터페이스 타입으로 선언했지만 내부에서 구현체를 직접 생성하면 변경 문제가 해결되는가?
2. 두 스레드가 Singleton의 같은 필드를 변경할 때 다른 요청의 값을 출력하는 실행 순서는 무엇인가?
3. `PaymentProcessor`의 생성 책임을 `OrderService` 밖으로 옮기는 생성자 주입 코드는 어떻게 작성하는가?

## 실행 결과 예측

- threadA가 `A`를 저장한 뒤 threadB가 `B`를 저장하면 threadA도 `B`를 출력할 수 있다고 예측했다.

## 예상의 근거

- Singleton 객체의 필드는 요청별 변수가 아니라 여러 스레드가 접근하는 같은 필드이기 때문이다.

## 실험

- 아직 실행하지 않음.
- 생성자 주입 코드를 학습자가 직접 완성한 뒤 최소 코드로 검증할 예정.

## 실제 결과

- 아직 실행하지 않음.

## 예상과 달랐던 부분

- `OrderService`를 사용하는 쪽에 `OrderService`를 주입하는 것과, `OrderService` 내부의 `PaymentProcessor` 생성 책임을 분리하는 것을 혼동했다.
- Java 생성자 선언의 괄호가 매개변수를 선언하는 자리라는 부분이 불명확했다.

## 내가 다시 설명하기

- 인터페이스 타입을 사용해도 구현체를 사용하는 클래스 내부에서 직접 `new`하면, 구현체를 바꿀 때 그 클래스를 수정해야 한다.
- threadA와 threadB가 같은 Singleton 필드를 공유하면 threadB의 대입이 threadA의 값을 덮어쓸 수 있다.

## 남은 질문

- `OrderService(PaymentProcessor processor)` 형태의 생성자 매개변수와 필드 대입을 직접 작성할 수 있는가?
- 구현체 교체 시 `OrderService`를 수정하지 않는 객체 생성 구조를 설명할 수 있는가?

## 회상 문제

1. 인터페이스 타입으로 필드를 선언하는 것만으로 생성 책임이 분리되지 않는 이유는 무엇인가?
2. `this.processor = processor`에서 왼쪽과 오른쪽의 `processor`는 각각 무엇인가?
3. Singleton의 변경 가능한 필드가 순차 요청에서도 문제를 만들 수 있는 이유는 무엇인가?
